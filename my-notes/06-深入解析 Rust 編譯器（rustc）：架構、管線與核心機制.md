# 深入解析 Rust 編譯器（`rustc`）：架構、管線與核心機制

Rust 之所以能在沒有垃圾回收（GC）的情況下，同時達成「記憶體安全」、「無畏併發」與「C/C++ 等級的執行效能」，背後最大的功臣正是它的官方編譯器——**`rustc`**。

`rustc` 不僅是一個將程式碼轉成機器碼的工具，更像是一位極度嚴格但友善的程式碼審查員。它本身是**自舉（Self-hosting）**的（也就是用 Rust 語言自己寫成的），並採用了現代化的**查詢驅動架構（Query-based Architecture）**。

---

## 一、`rustc` 的完整編譯管線（Compilation Pipeline）

與許多傳統編譯器（直接將語法樹交給 LLVM）不同，Rust 編譯器在前端與後端之間設計了**多層中間表示（Intermediate Representations, IR）**。每一層 IR 都專注於解決特定階段的問題，這讓 Rust 複雜的語法糖、型別推導與借用檢查得以優雅實現。

```text
原始碼 (.rs)
   │
   ▼  [詞法分析 & 語法分析 / 巨集展開]
  AST (抽象語法樹)
   │
   ▼  [去除語法糖 / 名稱解析]
  HIR (高階中間表示) ──► 型別推導 (Type Inference) & Trait 解析
   │
   ▼  [帶型別降階]
 THIR (型別化高階中間表示) ──► 模式匹配窮舉檢查 (Exhaustiveness Checking)
   │
   ▼  [轉為控制流圖 CFG]
  MIR (中階中間表示) ──► ★ 借用檢查 (Borrow Checker)、Drop 展開、Rust 專屬最佳化
   │
   ▼  [單態化 Monomorphization & 程式碼生成]
LLVM IR (或 Cranelift / GCC) ──► 底層硬體最佳化、生成原生機器碼
   │
   ▼  [連結器 Linker (lld / mold / ld)]
可執行檔 / 函式庫
```

### 1. 詞法與語法分析 → **AST（Abstract Syntax Tree）**
* **解析原始碼**：將 `.rs` 純文字切分成 Token，並建構成最貼近原始碼結構的抽象語法樹（AST）。
* **巨集展開（Macro Expansion）**：Rust 強大的宣告式巨集（如 `println!`、`vec!`）與程序巨集（如 `#[derive(Debug)]`）都會在這個階段展開成標準的 Rust AST 節點。

### 2. 去除語法糖 → **HIR（High-level IR）**
* **Desugaring（去除語法糖）**：Rust 提供了許多方便撰寫的語法糖（例如 `for` 迴圈、`while let`、`?` 錯誤傳遞運算子、`async/await`），在轉為 HIR 時會被簡化成更基礎的核心結構（例如 `for` 迴圈會被轉成 `loop` 加上 `match`）。
* **名稱解析與型別檢查（Name Resolution & Type Checking）**：編譯器在 HIR 階段確認每個變數、模組、函式的歸屬，並執行完整的**型別推導**與 **Trait 約束檢查**。

### 3. 型別化降階 → **THIR（Typed HIR）**
* 這是一個過渡層，將 HIR 進一步簡化並帶上完整的型別資訊。
* 最重要的任務是執行**模式匹配窮舉檢查（Exhaustiveness Checking）**——確保你的 `match` 語句涵蓋了 `enum` 或數值的所有可能分支，絕不遺漏。

### 4. 核心舞台 → **MIR（Mid-level IR）**
**MIR 是 Rust 編譯器設計史上最重要的里程碑（於 2016 年引入）**。它將原本的樹狀結構轉換成更貼近底層邏輯的**控制流圖（Control-Flow Graph, CFG）**。
在 MIR 層級，`rustc` 會執行以下關鍵任務：
* **借用檢查（Borrow Checking）**：分析每個變數的所有權轉移（Move）、借用（Borrow）與生命週期（Lifetimes），在編譯期徹底杜絕懸空指標與資料競爭。
* **Drop 展開（Drop Elaboration）**：精準決定每個擁有資源的變數在離開作用域（或提前 return / panic）時，應該在何處呼叫解構函式（`Drop::drop`）。
* **編譯期求值（CTFE / Miri）**：計算 `const fn` 與常數表達式的值。
* **Rust 專屬最佳化**：由於 LLVM 不懂 Rust 的所有權語義，先在 MIR 層做一輪內聯（Inlining）與死碼消除，能大幅減輕 LLVM 的負擔。

### 5. 程式碼生成與後端最佳化 → **LLVM IR 與機器碼**
* **單態化（Monomorphization）**：將泛型函式（例如 `fn add<T>(a: T, b: T)`）針對程式中實際用到的具體型別（如 `i32`、`f64`）分別複製並特化成獨立的函式。這是 Rust 達成「零成本抽象」的關鍵。
* **後端最佳化與連結**：將 MIR 翻譯成 LLVM IR，交由 LLVM 執行極致的底層最佳化（SIMD 向量化、暫存器配置、迴圈展開等），輸出目標平台的物件檔（`.o`），最後由連結器（Linker）打包成最終執行檔。

## 二、`rustc` 的四大核心機制

### 1. 查詢系統（Query System）與增量編譯
早期的編譯器通常是「一條龍」從頭跑到尾；但現代的 `rustc` 採用了**需求驅動（Demand-driven）的查詢系統**。
* 編譯過程被拆解成無數細小的「查詢」（例如：「查詢函式 A 的型別」、「查詢結構 B 的記憶體佈局」）。
* 當你修改了專案中某一行程式碼重新編譯時，`rustc` 會利用**增量編譯（Incremental Compilation）**快取先前的查詢結果，只重新計算受影響的依賴節點，大幅縮短開發期間的重建時間。

### 2. 借用檢查器的演進：從詞法到 NLL 與 Polonius
* **早期（詞法生命週期）**：參考的生命週期嚴格綁定在大括號 `{}` 作用域內，常導致許多「明明安全卻編譯不過」的誤判。
* **現代（NLL, Non-Lexical Lifetimes）**：引入 MIR 後，借用檢查器能沿著控制流圖精準追蹤「參考最後一次被使用的時間點」，大幅提升了寫程式的順手程度。
* **未來（Polonius）**：新一代基於資料流邏輯（Datalog 概念）的借用檢查器，正在逐步整合進 `rustc` 中，旨在解決目前 NLL 仍無法處理的少數邊界案例（例如在條件分支中提早回傳參考）。

### 3. 多樣化的程式碼生成後端（Codegen Backends）
雖然 **LLVM** 是 `rustc` 的預設後端，但 `rustc` 在架構上將「前端分析」與「後端程式碼生成」解耦，因此支援多種可抽換的後端：

| 後端名稱 | 特點與定位 | 適用場景 |
| :--- | :--- | :--- |
| **LLVM**（預設） | 最佳化能力極強，支援主流架構（x86, ARM, Wasm 等），但編譯速度較慢。 | 正式環境發布（`--release`）、追求極致效能。 |
| **Cranelift** | 純 Rust 編寫的輕量級後端，編譯速度極快，但產出的機器碼最佳化程度不如 LLVM。 | 開發階段的 Debug 編譯，大幅縮短等待時間。 |
| **GCC** (`rustc_codegen_gcc`) | 透過 `libgccjit` 呼叫 GCC 後端。 | 支援 LLVM 未涵蓋的冷門硬體架構（如部分舊款嵌入式晶片）。 |

*(註：除了官方的 `rustc`，社群中還有獨立開發的 `gccrs` 專案，目標是在 GCC 專案內直接實作一個獨立的 Rust 編譯器前端。)*

### 4. 業界標竿的錯誤診斷系統（Diagnostics）
`rustc` 的錯誤訊息被公認為程式語言界的典範，核心設計理念是**「將編譯器錯誤視為使用者體驗（UX）的一部分」**：
* **精準標示與上下文**：不只告訴你哪一行錯了，還會用彩色箭頭同時標出「所有權在哪裡被轉移」以及「後來又在哪裡被誤用」。
* **直接提供修復建議**：許多錯誤訊息會直接給出可套用的程式碼修改建議（甚至能搭配 `cargo fix` 自動修復）。
* **內建教學手冊**：每個錯誤都有專屬編號（如 `E0382`），只要在終端機執行 `rustc --explain E0382`，就能看到詳盡的原理說明與正確範例。

## 三、為什麼 Rust 編譯通常比較慢？（以及如何加速）

「編譯時間長」是 Rust 開發者最常討論的痛點。了解 `rustc` 的架構後，原因其實非常清楚：

1. **泛型單態化膨脹**：由於大量使用泛型與迭代器，編譯器必須複製出龐大的程式碼交給 LLVM 處理。
2. **LLVM 的深度最佳化**：LLVM 為了榨乾硬體效能，在編譯期投入了大量計算時間。
3. **編譯單元（Crate）較大**：Rust 以整個 Crate（而非單一檔案）為基本編譯與最佳化單位（雖有並行 Codegen Units 緩解，但相依鏈長時仍會形成瓶頸）。
4. **連結時間（Linking）**：大型專案將所有靜態函式庫連結成單一執行檔時，系統預設的連結器（如 GNU `ld`）往往非常緩慢。

### 實務上最有效的編譯加速技巧：
* **日常開發改用 `cargo check`**：只跑到前端的型別與借用檢查，完全跳過耗時的 LLVM 程式碼生成，速度極快。
* **更換高速連結器**：在 `.cargo/config.toml` 中設定使用 **`lld`**（LLVM 連結器）或 **`mold`**（Linux 上極速連結器），通常能讓重新連結時間減少 50%～80%。
* **善用 Workspace 拆分 Crate**：將大型專案拆分成多個獨立的小 Crate，讓 Cargo 能更充分地利用多核心 CPU 平行編譯與增量快取。
* **開發期試用 Cranelift 後端**：在 Nightly 版本中啟用 `rustc_codegen_cranelift`，可顯著加快 Debug build 速度。
* **使用編譯快取工具**：導入 **`sccache`**，在多個專案或 CI/CD 環境中共享已編譯的產物。

## 四、`rustc` 與周邊工具的關係

新手常會混淆 Rust 工具鏈中幾個核心元件的分工：

* **`rustc`（編譯器本體）**：負責把 `.rs` 原始碼編譯成機器碼。實務上開發者很少直接手動呼叫它。
* **`Cargo`（建置系統與套件管理器）**：專案的大管家。負責下載 `Crates.io` 上的相依套件、解析依賴樹、管理編譯設定，並在底層自動以正確的參數呼叫 `rustc`。
* **`rust-analyzer`（IDE 語言伺服器 / LSP）**：負責 VS Code、Neovim 等編輯器中的即時自動補全、跳轉定義與即時紅線報錯。它是一套獨立實作的增量前端分析引擎，專為「毫秒級即時互動」設計（未來正逐步與 `rustc` 共享更多核心函式庫，例如 Trait 解析器）。
