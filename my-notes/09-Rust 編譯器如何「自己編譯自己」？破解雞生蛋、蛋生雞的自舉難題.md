# Rust 編譯器如何「自己編譯自己」？破解雞生蛋、蛋生雞的自舉難題

在程式語言的世界裡，「**自舉（Bootstrapping / Self-hosting）**」——也就是用一種語言來寫它自己的編譯器——聽起來就像是標準的「雞生蛋、蛋生雞」悖論：

> **如果 `rustc` 是用 Rust 寫的，那在全世界還沒有任何 Rust 編譯器之前，第一份 `rustc` 是怎麼被編譯出來的？**

答案其實就像人類鍛造工具的歷史：**我們先用石頭敲出第一把粗陋的銅槌，再用銅槌打造出更精良的鐵槌，最後丟掉石頭，只用鐵槌不斷鍛造出更完美的鋼槌。**

以下我們分四個層面，完整拆解 Rust 編譯器的自舉奧秘。

---

## 一、歷史上的第一顆蛋：先借用別的語言（OCaml）

在 2006 年，Rust 創始人 Graydon Hoare 開始設計 Rust 時，世界上確實還沒有 Rust 編譯器。因此，他選擇了一個已經存在、且非常適合寫編譯器的函數式語言——**OCaml**，來打造歷史上第一個 Rust 編譯器。

這個歷史性的交接過程分為三個步驟：

1. **打造過渡工具（`rustboot`）**：
   開發團隊先用 OCaml 寫出了一個能看懂早期 Rust 語法的編譯器，稱為 **`rustboot`**。
2. **用 Rust 寫出新編譯器（`rustc`）**：
   有了 `rustboot` 之後，團隊開始用 Rust 語言本身，從頭撰寫正式的編譯器 **`rustc`**。
3. **完成歷史性交棒（2011 年）**：
   團隊用 OCaml 寫的 `rustboot`，把 Rust 寫的 `rustc` 原始碼編譯成了可執行檔。當這個 `rustc` 執行檔第一次成功編譯「它自己的原始碼」後，Rust 就正式達成了**自舉**！從此之後，`rustboot` 功成身退並被徹底刪除，Rust 程式碼庫裡再也沒有 OCaml 了。

```text
[OCaml 編譯器] ──編譯──► rustboot (用 OCaml 寫的早期 Rust 編譯器)
                             │
                             ▼ (編譯用 Rust 寫的 rustc 原始碼)
                         rustc v0.1 (第一個純 Rust 編譯器執行檔！)
                             │
                             ▼ (從此以後，OCaml 退場)
                         rustc v0.2 ──► v0.3 ──► ... ──► 現代 Rust
```

*(註：許多主流語言都走過這條路。例如早期的 C 語言編譯器是用組合語言與 B 語言寫的；Go 語言早期是用 C 語言寫的，直到 Go 1.5 才完成自舉。)*

## 二、現代 Rust 的「進化鏈」：用上一個版本編譯下一個版本

既然已經擺脫了 OCaml，那今天如果你下載了最新版（假設是 Rust 1.85）的 `rustc` 原始碼，電腦裡又沒有 Rust 1.85，要怎麼把它編譯出來？

Rust 採取的策略是**「版本接力」**：**永遠使用「前一個穩定版（或 Beta 版）」的編譯器執行檔，來編譯最新版的原始碼。**

為了確保新編譯器絕對可靠且能享受到自己新增的最佳化，Rust 的建置系統（`x.py`）會執行嚴謹的**多階段自舉（Multi-stage Bootstrapping）**：

```text
Stage 0 (前代編譯器，例如 Rust 1.84 執行檔，直接從網路下載)
   │
   ▼  編譯「Rust 1.85 原始碼」
Stage 1 (新版 Rust 1.85 執行檔，但是由舊版 1.84 編譯出來的)
   │
   ▼  再次編譯「Rust 1.85 原始碼」
Stage 2 (真正的 Rust 1.85 執行檔！由新版 1.85 自己編譯自己) ──► ★ 正式發布給使用者
```

### 為什麼不能只編譯一次（Stage 1），一定要跑到 Stage 2？
這是編譯器工程中非常精妙的設計：
1. **Stage 0（種子編譯器）**：它是上個版本的二進位檔，用來打破雞生蛋的迴圈。因此，Rust 官方規定：`rustc` 原始碼中只能使用「上一個穩定版已經支援的語法」，不能在編譯器裡偷跑使用「還沒編譯出來的新語法」。
2. **Stage 1（過渡版編譯器）**：它已經具備了新版的功能與最佳化邏輯，但「它自己這個執行檔」是由舊版編譯出來的，可能沒有享受到新版編譯器的效能改進，也可能藏著相容性問題。
3. **Stage 2（正式發布版）**：用 Stage 1 重新編譯一次新版原始碼。這不僅讓新編譯器自己吃到了新版的最佳化紅利，更是一次終極的壓力測試——**證明這個新編譯器真的有能力正確編譯像 `rustc` 這麼龐大複雜的程式**。
4. **Stage 3（可選的自我驗證）**：有時候為了抓出極難發現的編譯器 Bug，開發者會再用 Stage 2 編譯自己一次產出 Stage 3。理論上，**Stage 2 與 Stage 3 產出的機器碼應該要一模一樣（Bit-for-bit identical）**；如果不一樣，就代表編譯器本身有嚴重的非預期行為！

## 三、為什麼程式語言都執著於「自舉」？

既然用 C++ 或 OCaml 也能寫出 Rust 編譯器，為什麼 Rust 團隊要大費周章實現自舉？主要有四大好處：

1. **吃自己的狗食（Dogfooding）**：
   編譯器是世上最複雜的軟體之一。用 Rust 寫 `rustc`，能讓語言設計團隊每天親身體驗自己語言的痛點（例如借用檢查哪裡太囉嗦、哪裡缺乏好用的 API），直接推動語言變得更好用。
2. **極致的壓力測試**：
   每次對 Rust 語言或最佳化器做出修改，只要跑一次自舉，立刻就能用幾十萬行真實的工業級 Rust 程式碼來驗證有沒有改壞東西。
3. **享受語言本身的優勢**：
   `rustc` 本身是一個高度吃重效能與複雜資料結構的程式。用 Rust 寫編譯器，讓編譯器自己也享受到 Rust 的**高效能**、**記憶體安全**與**容易做多執行緒平行編譯**的優勢。
4. **降低社群貢獻門檻**：
   熟悉 Rust 的開發者不需要為了修一個編譯器 Bug，而額外去學 OCaml 或 C++，大幅壯大了 `rustc` 的開源貢獻者社群。

## 四、進階思考：自舉的資安隱憂與「打破死循環」的方法

自舉雖然優雅，但在資訊安全領域卻隱藏著一個極為著名的哲學與資安難題——由 Unix 共同創始人 Ken Thompson 在 1984 年圖靈獎演說中提出的**「信任的信任攻擊（Reflections on Trusting Trust）」**：

> **想像一下**：如果多年前某個版本的 `rustc` 二進位檔（Stage 0）被駭客植入了一個極為隱蔽的後門，這個後門會做兩件事：
> 1. 當它編譯一般程式（如登入系統）時，偷偷植入惡意程式碼。
> 2. 當它偵測到自己正在「編譯下一個版本的 `rustc`」時，**偷偷把這個後門也複製到新版 `rustc` 執行檔裡**。
>
> 那麼，就算你今天把最新版 Rust 的所有原始碼逐行審查一遍，確認「完全乾淨」，只要你還是拿前一個版本的二進位檔來編譯它，這個幽靈後門就會世世代代永遠潛伏下去！

### Rust 生態系如何破解這個難題？

為了解決「必須盲目信任歷史二進位檔」的問題，以及讓 Linux 發行版（如 Debian、Guix）能夠達成「100% 從純文字原始碼建置（Full-source Bootstrapping）」，社群發展出了**獨立的替代編譯器**：

* **`mrustc`（Mutabah's Rust Compiler）**：
  這是一個由開發者 John Hodge 完全用 **C++** 寫成的非官方 Rust 編譯器。它不需要任何現成的 Rust 執行檔！它的做法是把某個早期穩定版的 Rust 原始碼（例如 Rust 1.54）先翻譯成 C 語言，再用 GCC 編譯出來。接著，就可以從這個「完全由 C++ 驗證過、絕對乾淨」的 Rust 1.54 開始，一版一版（1.54 → 1.55 → ... → 最新版）一路接力自舉上來，徹底切斷對預編譯二進位檔的依賴。
* **`gccrs`（GCC Front-end for Rust）**：
  目前正在積極開發中的 GCC 官方 Rust 前端。未來一旦成熟，開發者就能用完全獨立的 GCC 工具鏈直接編譯 `rustc`，透過「雙重編譯器交叉比對（Diverse Double-Compiling）」徹底根除信任鏈攻擊的風險。

## 總結

Rust 解決「雞生蛋、蛋生雞」問題的完整脈絡，可以濃縮成三句話：
1. **起點**：先借別人的雞生第一顆蛋（用 **OCaml** 寫出 `rustboot` 來編譯第一個 `rustc`）。
2. **演進**：一旦孵化成功，就靠**版本接力**與 **Stage 0 → 1 → 2** 多階段編譯，讓前一代編譯器不斷鍛造出更強的下一代。
3. **安全防線**：透過獨立語言撰寫的 **`mrustc`（C++）** 作為備用起點，確保人類永遠有能力從零開始、不依賴歷史二進位檔重建整個 Rust 世界。
